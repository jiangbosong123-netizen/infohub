# 项目评估与第一轮完善

> 这是第一轮评估快照。用户确认以 AIHOT 主题页为目标后，主题系统、持久事件、发布方归一与增量索引已经实现，见 [后续实现说明](AIHOT_ALIGNMENT.md)。本文中对应的待办与预览状态以该说明为准。

评估时间：2026-09-12。范围：本地全部业务模块、模板和样式、README/SPEC、公司配置、部署配置、GitHub 仓库元数据与当前站点。没有逐条核验新闻事实，也没有重新请求全部外部新闻接口或调用 LLM。

## 判断

这是一个功能完整的个人信息聚合 MVP，抓取、公司匹配、AI 策展、热点、日报、搜索已经串起来了。FastAPI + Jinja2 + SQLite WAL 对当前规模合理；暂时不需要重写 React、拆微服务或引入消息队列。

当前更大的问题是内容筛选和可信度，而非缺少更多源。页面会混入低分公司消息、重复稿，AI 频道实际接收的是整个科技媒体的稿件，热点缺少稳定事件实体。用户仍然需要自己逐条筛选和判断，这会让产品显得像“信息列表”。

审查时的数据库快照：3,236 条信息，42 个启用源，其中 38 条未评分、136 条被判为非 TMT、2 条译标题使用失败占位符。42 个源的 fail_count 都是 0，但旧实现会把部分失败算作成功，且对账任务未写入相同的健康记录，因此不能把这个数字理解为全部链路正常。

GitHub 为私有仓库，默认 main，传统分支保护标记为 false；未进一步检查组织 rulesets。当前列表无 PR、issue 或 Actions 运行记录。本轮新增 CI 配置，但尚未推送执行。

## 架构梳理

```text
watchlist.yaml → companies → 动态公司源
                                ↓
cli.py / APScheduler → crawler → URL 归一、公司匹配 → SQLite items
                                                        ↓
                                                  AI 策展/补处理
                                                        ↓
                                        排名与热点重建 / 日报生成
                                                        ↓
                                         FastAPI → Jinja2 页面
```

优点：抓取器拆分清楚；SQL 参数化；SQLite 开启 WAL/外键；来源记录和公司关联已落库；无模型配置可降级；本地 launchd 已具备自动拉起能力。当前 Git 跟踪列表中只有 `.env.example`，没有 `.env` 和 data 文件，本次未读取密钥。

## 本轮已完成

| 问题 | 影响 | 修复 |
|---|---|---|
| SQLite 连接未显式关闭 | 长期运行依赖垃圾回收释放连接 | 保留原有事务行为并在上下文退出时关闭连接 |
| 日报用 +08:00 文本与 UTC 文本比较 | 日期边界偏移，漏收或跨日收录 | 报告日期转换到 UTC 后查询，并过滤非 TMT |
| 入库未统一时区 | 排序错误、无时区日期可能抛异常 | 入库统一 UTC，缺失/错误日期回退，保留未来日期钳制 |
| 先查再写去重有竞态 | 并行抓取同一 URL 时出现唯一键异常 | 冲突时幂等跳过，以实际插入结果计数 |
| 官方 RSS 输出 official=0 | 官方标识、加权和精选准入失效 | 入库同时读取来源 tier 判定官方身份 |
| AI 输出 ID、类型未校验 | 未知 ID 导致整批失败；补翻可写到批外条目 | 校验批内 ID、去重、严格布尔/分数类型、文本和分类校验 |
| 网络超时被当成内容过滤 | 条目永久跳过或错误隐藏 | 只有确认内容过滤才跳过，临时错误保留待重试 |
| 主 AI 流程缺少官方/公司兜底 | 与补处理规则冲突，官方条目可能隐藏 | 主流程与补处理统一保留逻辑 |
| 中文译标题未加入 FTS | 看得到却搜不到 | 增量 schema 升级、历史重建、更新/删除触发器同步 |
| 搜索可返回 tmt=0 | 与首页隐藏规则不一致 | 搜索统一过滤，短词包含译标题，LIKE 通配符按字面处理 |
| 译文失败占位符直接显示，负分参与热度 | 标题变成“-”，热度负数 | 页面/日报/热点回退原题，失败评分使用默认热度 |
| 公司关联绕过精选门槛 | 低分软文、趣闻大量混入 | AI 已配置时仅高分或官方进入精选；全量保留在全部动态 |
| 频道热点不跟着 Tab 变化 | AI/机器人页顶部仍是全站股票热点 | 首页热点按频道过滤 |
| 翻页丢失分类、刚好 60 条也显示下一页 | 筛选跳变或进入空页 | 保留分类，额外查询一条判断下一页 |
| 源失败被 CLI 显示为成功 | 监控误导 | 传递实际执行状态；部分失败可见，成功条目保留 |
| 声称退避但未实现 | 故障源持续按原频率重试 | 指数退避并设置上限 |
| 健康页长时间没更新仍显示正常 | 难发现调度停滞 | 超过三倍基础间隔（至少 15 分钟）标记延迟 |
| 日报 Markdown 原样输出 HTML | 外部内容可产生脚本/危险链接 | 使用 nh3 清洗渲染结果；入库限制 HTTP(S) URL |
| 导航没有 active 状态、窄屏布局拥挤 | 不知道所在位置，搜索和热点容易挤压 | 路径驱动导航状态、移动端折行、表格横向滚动、焦点提示 |
| 没有自动回归 | 修改容易破坏抓取/筛选 | unittest 测试与 GitHub Actions；限制 APScheduler 主版本 |

以上不会自动重算历史 AI 判定、修复历史 official 字段或重生成历史日报。历史内容改写应通过一次性迁移或明确的重处理命令执行，保留备份与计数。

## 接下来最值得做的三件事

### 1. 稳定事件实体和真正的多信源

当前 `ranking.py` 每轮删掉所有簇再重建，ID 不稳定；链接锚点可能失效或指向另一事件。相似度比较原始标题，跨语言报道难合并，同一公司例行文件又容易误合并。`source_count` 按采集源名称计数，Google News 公司源与真实发布媒体不是同一层级：同一媒体的多个入口可能被算多家，多家媒体也可能被折叠成一家。

建议新增持久化 `events`，让 `event_items` 管理报道归属，保留稳定事件 ID、首发时间、最近进展时间；从 Google News 的 `extra.publisher` 提取发布方，与抓取入口分开存。先用公司、事件类型、日期、标题词重合产生候选，再评估是否需要 embedding；不要直接用模型替代所有规则。

验收：固定一组同事件/不同事件样本，验证重复折叠、跨语言归并、不同财报期不合并；重复抓取后事件 URL 不变；信源数可点开核对到真实发布方。精选以事件卡展示“发生了什么 / 为什么重要 / 最新进展 / 原始来源”。

### 2. 公司跟踪与阅读闭环

现有公司标签只把用户带回筛选列表。建议第一版公司详情包含“近 24 小时重要事件、官方公告、按时间排列的进展”；增加收藏、已读、稍后读，先在本机 localStorage 实现。首页提供最近更新与尚未阅读的重点；自动刷新改成“有新内容，点击更新”，避免阅读时整页跳动。

AI/机器人/股票不应完全沿用采集源固定频道。建议条目增加多标签，抓取源只作为默认候选，AI/规则判定实际主题，避免普通手机促销长期占据 AI 频道。公司别名如“微信”“马斯克”只是实体线索，不应自动等于公司经营事件。

验收：从任一公司标签进入稳定公司页；切换筛选和翻页不丢状态；收藏刷新后保留；新内容不会打断正在阅读的文章；从精选中能查看全部报道。

### 3. 可追溯 AI 与可靠运维

目前 `summary` 被 AI 覆盖，原始摘要丢失；缺少模型版本、提示词版本、处理状态、重试次数、成本与延迟记录。部分条目只提供标题/极短摘要，模型写出的推荐理由可能超出证据。应拆分 raw_summary / summary_zh，新增 `ai_jobs` 与处理审计，规定结论不得超出素材，日报每条保留来源链接。先建立人工标注的小型质量集，再比较模型。

同时增加 SQLite 定时备份及恢复演练、统一任务运行记录、调度心跳、失败/积压可视化。`run_reconcile` 尚未调用标准源健康记录；HKEX 无法解析 stockId 会返回空列表，SEC 部分缺失 CIK 会静默跳过；这些仍可能产生“没消息”和“抓不到”混淆。下一轮应逐公司记录成功、失败、空结果。

验收：任一 AI 摘要可回溯原文与生成版本；重试有预算与上限；对账失败能在健康页看到；能在空目录恢复备份并打开页面；模拟睡眠/调度停机后出现明确延迟状态。

## 其他架构与部署边界

- 调度器在 `cli.py serve` 中创建，直接 `uvicorn app.web.routes:app` 只提供网站，不会运行抓取。未来扩展时拆成单独 worker，避免每个 web worker 都重复抓取；目前坚持单实例即可。
- `process_pending` 新条目优先，在持续高峰下老条目仍可能饥饿；“去掉日期限制”不等于保证最终处理。应按新旧队列配额调度。
- 日报依赖最近 48 小时的临时 clusters，历史重生成无法完整重现当天热点。需要事件持久化或日报素材快照。
- 同域提交错峰在代码中多数为 0.3 秒，只有 Yahoo 为 3 秒，并不是 SPEC 所说所有同域 3 秒。后续将限速移到 HTTP 层，以实际请求为准。
- 抓取条数与时间窗口有限，睡眠恢复、Google News 对账不能证明“100% 不漏”。已下调 README/SPEC 的绝对覆盖表述。
- launchd 的绝对路径绑定当前 Mac，适合个人本机使用；若要远程访问/多人使用，再补配置化部署、身份认证、限流和日志脱敏。
- 依赖目前多数只设最低版本。此次仅约束已知 APScheduler 3.x API；后续建立受验证的依赖锁定与升级流程。
- 数据库各个旧版本迁移尚无正式版本表；这次搜索索引迁移已保持幂等和事务边界。未来新增字段较多时引入 schema_version 和独立迁移脚本。
