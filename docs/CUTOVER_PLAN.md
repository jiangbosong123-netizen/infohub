# 生产升级方案（基于 2026-10-04 完整演练）

本页把 v1 新结构第一次真正上线所需的决定、步骤、耗时、停机窗口和回退写在一起。数字来自
[`docs/evidence/cutover-rehearsal-20261004.json`](evidence/cutover-rehearsal-20261004.json)：在本机旧库的隔离副本
（89,575 条，2026-09-11 至 2026-10-03）上，用 `main` 的代码从 schema 0 走到 schema 46，全程不联网、不调用模型。

## 1. 现状

- 两台机器都**没有在采集**：Mac 旧的 `com.infohub.server` 自 2026-10-03 17:02 起崩溃重启，已按所有者要求停用；
  Tailscale 上 `windows-server` 离线。
- 本机 `data/app.db` 是旧结构（schema 0），完整保存 2026-09-11 至 2026-10-03 的 89,575 条；Windows 生产库的内容与
  时间范围目前无法查看。
- 新结构代码全部在 `main`，默认关闭的开关保持关闭；生产从未升级。

## 2. 需要所有者决定的两件事

1. **哪台机器做生产。** 默认是 Windows Docker Compose（`docs/RUNBOOK.md`）；备选是本机 launchd
   （[`deploy/macos/`](../deploy/macos/README.md)，已在隔离目录测试）。**两台不能同时采集**（SPEC §3），Mac 脚本检测到
   Windows 在线会拒绝启动。
2. **哪份数据成为生产数据。** 本机旧库与 Windows 库各自独立采集过，不能合并成一个数据集（同样是 SPEC 的否决方案）。
   Windows 上线后先只读比较两边的条目数、时间范围与来源，再选一份；另一份作为只读归档保留。

选定 Windows 后的逐条命令见 [Windows 生产升级手册](WINDOWS_CUTOVER.md)（含安全开机、关闭自动部署、只读检查与回退）。

## 3. 升级步骤与耗时

| 步骤 | 演练结果 | 耗时 | 门户 | 采集 |
|---|---|---|---|---|
| 迁移前一致性备份 + 迁移到最新 schema（`prepare-release`；演练时为 46，schema 47、49 只重建触发器，schema 48、50 只建索引，在旧库上耗时可忽略） | 成功；首次需把旧 `titles-v2` 聚类全部重算 | 演练 5 分钟（285–294 秒）；之后重新聚类的打分缓存每条新闻的特征并跳过不可能胜出的标题对，同机对照 300 → 226 秒、结果逐表一致，预计约 4 分钟 | **停** | **停** |
| 启动 web + worker | 门户 200；`/api/ready` 需 worker 心跳 | 迁移后首次 1 分钟内；库变大后每次启动都先完整校验数据库：4.9 GB 时 Mac 热缓存约 34 秒（演练时约 3 分钟），冷缓存或 Windows Docker 挂载目录更慢 | 可用 | 恢复 |
| 历史回填 `legacy-backfill` | 89,575 条 / 103,112 发现 / 22 日报，0 缺失 | 演练 19 分钟；复用连接后同机 2.5 分钟（147 秒，逐次新建连接对照 1,237 秒） | 可用 | 建议暂停 worker |
| 主题回填 `legacy-topic-backfill` | 95,203 条，0 缺失 | 演练 16 秒；同机约 10 秒 | 可用 | 同上 |
| 事件转换 `legacy-event-project` | 76,572 故事 → 72,676 事件 | 18–21 秒 | 可用 | 同上 |
| 旧 AI 策展导入（358,300 个任务） | 358,300 个全部成功（待复核 358,174 / 证据不足 62 / 拒绝 64），中断 3 次均自动续跑 | 演练：排队 15 分钟 + 处理约 2.5–3.5 小时（约 30–40 个/秒）；现在同机从零排队并处理完 18 分钟（1,094 秒，结果分布与演练相同，见第 7 节） | 可用 | 同上 |
| 搜索 / 热度 / 主题统计构建 | 搜索 89,575 条、热度 76,572 个事件、主题统计 56 个 | 约 2.5–3 分钟 | 可用 | 可恢复 |
| 审计 + 备份包 + 隔离恢复 + 门户冒烟 | 全部通过（旧表对照有两项已解释差异）；备份包 4.9 GB 隔离恢复后 8 个页面全部 200 | 审计约 6 分钟；打包、校验、恢复、冒烟约 36 分钟（可在线进行） | 可用 | 可恢复 |

**停机窗口只有迁移这一步**（演练约 5 分钟，现在预计约 4 分钟，网站与采集都停）。之后门户立即可用；回填与导入只写新的版本化表，旧门户
读取的投影不受影响。为避免与 worker 争用 SQLite 写锁，建议回填期间只运行 web，约 25 分钟（Mac 同机实测：回填到构建共约 24 分钟；演练旧版本为 3.5–4 小时）后再启动 worker
恢复采集；如果更在意采集连续性，也可以先启动 worker，回填会因写锁等待变慢但不会出错（持久任务可续跑）。

## 4. 演练中发现并已修复的问题

| PR | 问题 | 结果 |
|---|---|---|
| #150 | 首次升级重算全部旧聚类时，每条新闻对上万个候选全量排序 | 初始化 606 s → 285 s；聚类结果逐字节一致 |
| #152 | 任务领取每次把整个积压排序（schema 45） | 34.8 万积压时单次领取 93 ms → 0.03 ms；领取顺序不变 |
| #153 | 发布幂等检查与每日预算汇总全表扫描历史（schema 46） | 15 ms → 0.002 ms；结果一致 |
| #154 | 门户冒烟测试挑中没有公开报道的事件，误报 404 | 改为与门户相同的判断条件 |
| #151 | Mac 部署脚本：缺私网 HTTPS 地址；`.env` 中带空格的值导致 worker 起不来 | 测试中发现并修复 |

导入速度：未修复时 9.4 个/秒（约 10 小时）→ #152 后约 30 个/秒 → #153 后约 39–41 个/秒。

## 5. 已解释的差异（不是错误）

- `items.channel` 107 行、`sources.channel` 1 行变化：来源配置把 `openai-news` 从股票频道改为 AI 频道，初始化按配置
  同步并重新归类历史条目（`app/crawler/runner.py` 的刻意设计）。其余旧表列一个值都没变。
- `stories` / `story_items` 变化：旧 `titles-v2` 聚类升级为 `titles-v3`。
- 29,026 个没有公开报道的事件（升级前就有 29,029 个）：成员被重新判定为非科技后，门户按设计显示“暂无公开报道”。

## 6. 回退

1. 停止 web 与 worker。
2. 代码回到上一版本；新库的 schema 高于旧代码时，旧代码会拒绝启动（保护）。
3. 用迁移前自动生成的备份（`data/backups/`）恢复数据库；恢复前保存当前文件。若恢复后曾对外同步，按
   [发布账本说明](PUBLICATION_LEDGER.md) 处理 epoch。

## 7. 仍未覆盖的事项

- Windows 机器离线，未做 Windows 现场演练；Windows 库内容未知。
- 没有启动真实 worker（会抓取并调用付费模型）；首次正式启动即是 worker 就绪测试。
- 每个任务约开 10 次数据库连接，每个新连接的第一条语句都要解析约 740 个 schema 对象（约 1.8 ms）。`legacy-curation-run`
  与 `projection-builders-run` 现在在同一线程内复用已提交的连接：在演练规模的副本上抽样 3,000 个导入任务，从约
  30 ms/个降到 6.6 ms/个（约 150 个/秒）；300 条的对照导入中，复用与逐次新建连接的结果逐项一致。之后又发现每次授权的
  当天预算求和会重扫当天全部 0 元授权（25 万个时约 10 ms/个），改为跳过 0 元行后，同一副本 25 万规模下约 4.6 ms/个且不再
  随数量增长。`legacy-backfill` 与 `legacy-topic-backfill` 也在同一作用域内运行（历史回填每条约 5 次连接，
  1,237 → 147 秒，全部 146 张表除时间戳外逐行一致）。同机从回填到构建完整实测约 24 分钟。
  web 与 worker 仍每次操作新建连接。
- 新读取开关在导入与审计通过后逐个开启。演练中在恢复出的副本上开启策展读取、新搜索、新热度后，首页、全部、热点、
  搜索（中英文）、日报与健康页均为 200；**主题读取开关**在没有经所有者批准的主题统计准入时会返回 503（按设计不显示
  未审核数字），开启前需先完成主题抽样复核与准入（`docs/TOPIC_STATISTICS_ADMISSION.md`）。日报与 API 开关各自仍有验收要求。
  演练只检查了状态码；之后实测开启策展读取时精选首页要 9.8 秒、股票频道 14 秒，已改为流式读取（首页约 40 ms，结果逐行
  不变，见 `docs/CURATION_CONTRACTS.md`）。只开策展读取、未开主题读取期间，主题列表仍需约 1–5 秒。

## 8. 所有者需要亲自做的事

1. 选定生产主机与生产数据（第 2 节）。
2. 若选 Mac：手动开启 Tailscale Serve（`deploy/macos/README.md`）；若选 Windows：开机并让部署管理器只部署 CI 通过的 `main`。
3. 开启主题读取前，完成一次主题抽样复核与准入。
4. 正式升级当天确认停机窗口（约 4–5 分钟）与回填期间是否暂停采集。
