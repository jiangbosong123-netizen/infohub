# 架构决策、待定问题与否决记录

日期：2026-09-14。以下“基线决策”表示本SPEC提出的明确设计，**不代表所有者已逐条批准或生产已实施**。批准后作为后续PR的约束；改变时追加ADR，记录原因和兼容影响，不无声改口径。

## 1. 基线决策

| ID | 决策 | 依据与代价 |
|---|---|---|
| D01 | 保留Python/FastAPI/Jinja2和模块化单体 | 当前规模约1.1万条，问题主要在数据语义与边界。避免重写引入迁移风险；需要明确查询/采集/分析模块接口 |

## 5. 追加决策记录

### D23 单人所有者标注协议 `single-owner-v1`（2026-10-03）

**问题。** 现有评估代码把 `publishable_gold` 定义为：两名不同的独立 reviewer、第三名不同的 adjudicator，
tone/impact 还要第四名独立的私有证据复核人；tone 发布决定和激活人也必须与标注者不同。项目只有所有者
一名人工标注者，这些门槛永远不可达。结果是 tone 的整条发布链（metrics → calibration → release
admission → activation）以及“`valid` tone 结果必须对应 active release”都被永久阻塞；所有者也没有任何
路径产出可用的标注数据，连 experimental 结论都做不出。SPEC §8.2 与 D16 已写明“单人标注只能
experimental”，但代码里的 `single_annotator` 只是等待裁定的临时状态（labels 必须为空），没有实现这一层。

**现状证据。** 本机 `data/app.db` 有 89,575 条真实旧库条目（2026-09 至 2026-10），可用现有
`evaluation_sampling`/`evaluation_admission` 抽样；没有任何真实标注；没有把评估 case 渲染给标注者阅读的
工具（只有主题复核有本地工作台）。三个 checked-in 数据集都是合成 fixture。

**候选方案。**
1. 维持多人门槛，等待第二、第三名标注者：不可执行，无限期阻塞。
2. 同一人换不同 reviewer ID 扮演多人：违背“独立”本意，否决。
3. 让 LLM 生成 gold 并自评：§3 已否决的自证循环。
4. 分层：保留多人 gold 定义；新增所有者盲标的 owner 层和算法生成的 silver 层，各自有明确用途与禁止项。

**选择方案 4。** 三层标注，层级只能由显式流程产生，不能隐式升级：

| 层 | 产生方式 | 允许用途 | 禁止 |
|---|---|---|---|
| gold | 现有双人独立 review + 第三人裁定（+ tone/impact 私有证据复核） | 正式质量结论、tone `valid` 发布链 | 保持现状；在有第二名标注者前不可达 |
| owner | 所有者在不看任何模型/算法输出的情况下盲标，hash 绑定导入，`model_assistance=false` | experimental 质量结论；评估任何模型（含算法标注器）的真值 | 不得称 gold、不得满足 `publishable_*_gold`、不得驱动 tone `valid` 发布 |
| silver | 版本化算法标注器（规则或模型）批量生成，记录 labeler 版本与配置 hash | 只进 train/dev：调参、训练、覆盖面检查 | 不得进入 test/security；不得作为任何评估真值；不得评估生成它的标注器本身 |

owner 层规则：

- **盲标。** test split 的 owner 标签必须盲标。所有者若在看过算法标签后确认或修改（适合量大的 train/dev），
  记录为 `model_assistance=true`，仍属 silver 层。
- **延时自复核（替代第二名标注者）。** 按固定种子从 owner 标注的 test case 中抽取 `max(30, ⌈10%⌉)` 条
  （不足则全部），在首次标注至少 7 天后由所有者在看不到首次标签的情况下重标。关键标签（relevance 标签、
  tone polarity、impact direction）的同人 Cohen κ 目标 ≥0.70，至少 30 对；未达标先修标注定义，不调门槛。
  不一致的 case 由所有者在看过两次标签后写出最终决定与理由，仍属 owner 层。
- **experimental 结论条件。** 被评估 split 为 test 且全部是盲标 owner case；blind-holdout 时 holdout review
  已核验；自复核完成且 κ 达标；预测完整、失败/拒判进入分母。报告必须标明 `annotation_tier=owner`、
  “单人标注、同人一致性非双人一致性”，逐类和切片 support <30 标低支持。
- **向 gold 兼容。** 若将来有第二名标注者，owner 盲标可作为其中一份独立 review 导入；不会自动成为 gold。

silver 层规则：标注器必须版本化（代码/提示词/模型 ID 的 hash）；每次使用前先在 owner test 集上按普通模型
评估并公开其指标；silver 与 owner 标签分别存放、分别计数；任何基于 silver 的数字只能称“与 silver 的一致率”，
不能称准确率。

**影响。** 不改变生产数据、ID、时间或 API；不改变 gold、tone 发布链和 `valid` publication 的任何现有条件。
新增的是评估数据集里的标注状态、导入/自复核/指标代码和本地标注工具，均为评估目录内的私有数据。

**迁移与回滚。** 新状态只出现在新生成的私有数据集版本中；旧版本与合成 fixture 不变。回滚即停止使用新状态，
已有 owner/silver 数据集保留为历史版本，不改写为其他层。

**评估结果。** 尚无。第一条真实链路计划以 relevance 为起点（已有抽样、准入和 `relevance-rule-v0` 基线）。

**批准状态。** 所有者 2026-10-03 在会话中确认：主要由本人标注，数量过多时由算法标注；实现者按小 PR 推进。

**生效 PR。** 本记录所在 PR 只确立协议；状态、导入、自复核、指标与标注工具在后续 PR 中逐项实现，
实施进度见 [`IMPLEMENTATION_STATUS.md`](IMPLEMENTATION_STATUS.md)。

### D24 日常采集的观察记录保留 `observe-on-change-v1`（2026-10-06）

**问题。** [INGEST_EVIDENCE](../INGEST_EVIDENCE.md) 规定同一来源、locator 与载荷 hash 复用一条 `raw_record`，
但每次执行仍追加一条 `raw_observation`；该表由触发器保护为只增不改。来源每 10–60 分钟返回最新几十条，
其中绝大多数是已经存过、内容没有变化的条目，因此这张表的增长与“轮询次数 × 每页条数”成正比，
而不是与新内容成正比。[DATA_MODEL](DATA_MODEL.md) 已预留“可按保留策略压缩计数”。

**现状证据。** 隔离库实测：一次 50 条全部已存的执行追加 50 行 observation；每行连同 3 个索引约 370 字节。
按 Windows 常开、现有来源频率估算每天约 12 万次观察（23 个 Google News 源每 20 分钟各至多 50 条占一半以上），
约 47 MB/天、15–17 GB/年；作为对比，演练规模的整库为 4.9 GB。备份、完整校验与磁盘占用随之线性增长。

**候选方案。** A 保持每次追加；B 只在首次看到或内容变化时追加；C 全部追加、定期压缩旧明细（需放开不可变触发器）。

**选择与理由。** 选 B。日常采集（`run_source` 与 Google News 对账）调用 `observe_candidate(repeat_unchanged=False)`：
当该来源对这个 locator 最近一条 observation 已是同一条 raw record 时不再追加。新 locator、新内容、以及从变化后
的内容回到旧内容（A→B→A 的最后一次）都照常追加，所以内容变化的完整时间线仍在 observation 中。重复看到的事实
由三处保存：`ingest_runs` 的重复计数、`document_locators.last_observed_at`（取已有 observation 与本次看到时间中
较晚者，与逐次追加时的值相同）、旧投影 `item_discoveries.last_seen_at`。不再保留的只有“每一轮都看到它”的逐轮明细。
旧数据回填等其他调用方保持默认的逐次追加，因为它们的崩溃恢复和计数依赖逐条 observation。

**什么算内容变化。** 规则按载荷 hash 判断，因此载荷里不能有每次轮询都会变的字段。同一批条目隔 5 分钟重抓：
新浪 7x24 44/44、华尔街见闻快讯 46/46、TechCrunch 19/19、IT之家 60/60 载荷不变；Google News 135 条中 4 条变化，
都是发布方更新了标题或发布时间，属于真实变化，照常追加。财联社电报 18/18 全部变化，原因是阅读数等互动计数
（包括关联专题的关注人数）。这些计数描述读者而不是电报内容，因此财联社证据记录不再保存 `reading_num`、
`comment_num`、`share_num` 与 `subjects[].attention_num`，专题本身仍保留。此前它们让财联社每次轮询都生成新的
raw record、CAS 对象与 `document_version_inputs` 行（文档版本本身不受影响），这一点与是否逐次追加 observation 无关。

**影响。** 已有 observation 不改不删；ID、时间语义与 API 不变。首次看到时间、内容变化时间线、locator 最近看到
时间与逐次追加时一致；不再能从 observation 逐轮重建“某一轮是否列出了未变化条目”。估算增长：首次看到约每天
5 千条（约 0.7 GB/年），加上每次执行仍写的运行记录与抓取日志（约 0.5 GB/年），合计约 1.2 GB/年。

**迁移与回滚。** 无 schema 迁移。回滚即恢复默认参数；回滚前未追加的重复观察不会补出，期间的重复看到仍保留在
运行计数与 locator 时间中。

**评估结果。** 五轮采集（新增、不变、部分修改、改回、不变）在两种规则下，除 observation 表外每张表内容一致；
observation 从 100 行降为 30 行，locator 首次/最近看到时间与逐次追加时相同（`tests/test_observation_on_change.py`）。
一次 50 条全部已存的执行不再追加 observation，耗时约 28 ms 不变。

**批准状态。** 所有者 2026-10-06 在会话中选择方案 B。

**生效 PR。** 本记录所在 PR。
