# 架构决策、待定问题与否决记录

日期：2026-09-14。以下“基线决策”表示本SPEC提出的明确设计，**不代表所有者已逐条批准或生产已实施**。批准后作为后续PR的约束；改变时追加ADR，记录原因和兼容影响，不无声改口径。

## 1. 基线决策

| ID | 决策 | 依据与代价 |
|---|---|---|
| D01 | 保留Python/FastAPI/Jinja2和模块化单体 | 当前规模约1.1万条，问题主要在数据语义与边界。避免重写引入迁移风险；需要明确查询/采集/分析模块接口 |
| D02 | SQLite继续作为首期主库；web与worker分进程 | 保留生产兼容并隔离调度。只有一个writer，长计算在事务外；多主机扩展时另评估PostgreSQL |
| D03 | 采集保存与相关性/精选分开 | 当前tmt隐藏宏观材料，不适合未来研究API。增加存储与后续治理成本，需来源/内容权限边界 |
| D04 | raw→document revision→event version→analysis→signal均可追溯 | 现有摘要覆盖、同URL忽略更正和NLP UPSERT无法支撑研究；增加表和原始对象存储，但不是一次性全部实现 |
| D05 | 文章、实体、主题、事件多对多 | 单story_id不支持一篇多事件；主体别名不同于主体身份；迁移旧story为candidate并保留链接 |
| D06 | 文档去重、事件聚类、来源独立性分层 | 同报道不一定独立，同公司不一定同事件。不能用多源数量替代证据可靠性 |
| D07 | 发布/观察/事件/可见时间分开，支持as_of | 下游历史分析不能混入晚到新闻与未来模型输出。历史资料无法补齐时标PIT不合格 |
| D08 | NLP attempts/results追加，当前值是publication投影 | 可比对模型与人工修正；重跑额外存储和费用显式记录，模型完全复现不保证 |
| D09 | tone与impact分任务，unknown是正常结果 | 情绪、经营影响、股价变化是不同问题；首期不输出交易决策 |
| D10 | 人工动作有版本与乐观锁，优先于自动结果 | 防重跑覆盖与多人冲突；原分析仍保留，人工不改写证据 |
| D11 | 任务至少一次执行+幂等发布+租约fencing | 外部网络/模型不可保证exactly-once，重试成本必须审计 |
| D12 | v1浏览分页与可靠同步分开 | published_at游标不能捕捉晚到/修正；同步用snapshot+change_seq+epoch |
| D13 | 集成API最小scope token，私网加HTTPS | Tailscale只解决连通与网络访问，不表示所有应用调用同身份。首期不建多租户平台 |
| D14 | 扩表、回填、对照、切读、延后删表 | 保留正在运行的数据与旧页面；牺牲短期简洁换取可回滚演进 |
| D15 | 部署管理留在独立仓库 | 多系统共用部署，InfoHub只提供镜像/迁移/检查接口；跨仓库关联PR要明确依赖 |
| D16 | 每个领域能力先有gold样本与发布门槛 | 当前离线单测不证明真实NLP质量。单标注者的impact保持experimental |
| D17 | 首期宏观覆盖为科技/行业相关领域 | 当前源结构偏科技企业，不能声称代表整体市场；广义宏观逐源扩展 |
| D18 | 首期叙事情绪汇总按事件等权，质量/未知分开输出 | 避免转载和未校准confidence放大分数；候选公式需评估，不能包装成收益预测 |
| D19 | 不合并PR #1原设计；拆分替代PR | 方向部分可取，但迁移事务、审计覆盖与同步语义需先修改 |

U01–U05需在R1生产验收前解决；U06–U12按领域阶段解决。无需一次回答所有问题才能开始写迁移工具或修部署状态机，但不可跳过依赖关口。每个待定项由项目所有者作产品/成本选择，实现者提供测量证据和具体候选。

## 3. 本阶段否决/推迟方案

| 方案 | 结论与原因 | 重审条件 |
|---|---|---|
| 只仿AIHOT页面，继续用items可变字段承载全部分析 | 否决：无法支撑溯源、多任务、修正与下游稳定接口 | 无；页面仍可参考其信息组织 |
| 全量重写/立即上微服务、Kafka、Kubernetes、向量数据库 | 推迟：没有规模或团队证据，扩大Windows运维负担 | 单库有实测瓶颈/多主机需求；先遵守模块接口 |
| 立即迁PostgreSQL | 推迟：当前数据量不构成理由，先修事务与查询 | 根SPEC的锁等待/失败阈值持续触发，或多主机要求 |
| 所有非TMT数据直接过滤或删除 | 否决：宏观/研究材料与首页不同 | 仅安全/来源授权要求可限制，不由策展分删除 |
| 把AI摘要当原文或补造旧模型审计 | 否决：制造虚假证据 | 无 |
| 同一pipeline只存最后一个NLP结果 | 否决：无法比较模型、重建历史、保留人工修正 | 可保留“当前投影”，但不是唯一记录 |
| 发布时间since作为全量变化同步 | 否决：漏晚到、修正、撤回 | 仅保留浏览过滤用途 |
| 多家报道直接提升可信度/同标题直接confirmed | 否决：转载同源、同实体不同事件 | 有来源链与gold评估后可作为候选特征 |
| 统一利好/利空字段代表文本/经营/市场影响 | 否决：对象、方面和期限缺失 | 新任务与独立schema定义后分别实现 |
| 用LLM自己标gold并自己评估 | 否决：自证循环 | AI仅可预标，正式标签有人评与裁定 |
| 把Git pull成功当部署成功 | 否决：镜像/迁移/就绪可在之后失败 | 无，需独立健康版本状态 |
| 直接复制运行中app.db，或只回退Git就叫无损恢复 | 否决：WAL和schema/新写入未处理 | 一致性备份和兼容恢复演练通过 |
| 大系统直接读写Windows SQLite文件 | 否决：泄露存储细节且多机并发风险 | 使用稳定API或受控离线snapshot |
| 同时从Mac和Windows采集写同一生产数据集 | 否决：身份/序列/任务所有权冲突 | 若将来分布式采集，有独立raw入口与统一身份事务 |
| 本阶段公开互联网部署、多租户、交易执行 | 不在范围内 | 明确产品、安全和资源要求后另提SPEC |

## 4. 决策变更格式

新增记录包含：问题、现状证据、候选方案、选择与理由、对生产数据/ID/时间/API的影响、迁移与回滚、评估结果、批准状态和生效PR。模型与提示词变动也需版本记录，但只有改变产品含义或关键口径时才升级为架构ADR。

本SPEC本身通过审阅后应锁定一个Git提交作为v1基线；后续SPEC修改与代码改动在同一PR评审。文件名中的“正式”指结构和可执行程度，不表示未经审阅就自动成为生产事实。
