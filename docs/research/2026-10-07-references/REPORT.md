# 先堵 SQLite 漏洞，再分三批借鉴开源做法

最该先做的一件事不是引入新框架，而是一个版本号：SQLite 官方 2026 年 3 月公布的 WAL-reset 损坏 bug 覆盖 **3.7.0 到 3.51.2** 的所有版本，触发条件是"WAL 模式下两个以上进程或线程的连接同时写或 checkpoint"，这正是 infohub 的 web + worker 双进程形态；仓库 `.venv` 里的 SQLite 是 3.51.0，Docker 基础镜像 `python:3.12-slim` 所用的 Debian 版本也都落在受影响区间（[SQLite WAL 文档](https://sqlite.org/wal.html#walresetbug)）。其余借鉴分三批推进。**本周**做四件小事：按主机遵守 `Retry-After`、给 RSS 加条件请求、加一个机器外的 dead-man switch、把财联社签名的参照从 AGPL 的 RSSHub 换成 MIT 的 newsnow。**本月**做四件：补评测统计（Wilson 区间、ppi_py、cleanlab），把 0–100 的重要性分改成带锚点的 0–5 级并用站长标签校准，给 titles-v3 加时间特征和定时合并，再调几项 SQLite 运维参数。**本季度**做跨语言 story 链接、监管事件标签、日报 claim 级溯源和覆盖率监控。证据最硬的有三条。第一，在同语种的事件聚类上，词面 + 实体 + 时间特征仍然胜过单独的 embedding。第二，LLM 判相关性比人宽松，所以首先要盯误报。第三，120 条测试集只能发现大错（准确率的误差约 ±6 个百分点），再好的统计方法最多把标签效率提高约一倍。许可证方面，Miniflux、newsnow、Huginn、reader、Healthchecks、trafilatura、edgartools、ppi_py、cleanlab（2025 年 12 月起）的代码都可以直接复用；RSSHub、FreshRSS、TrendRadar、GNE 只能读思路，不能抄代码。infohub 已有的几样东西已经和成熟项目同构，不必重做：指数退避、静默源检测、快讯回补、租约 fencing、不可变证据。

有几样东西明确**暂不做**。WebSub：探测过的 infohub 信源没有一个声明了 hub，而且订阅方必须提供公网可达的回调地址、做 intent 验证、续租（[W3C WebSub](https://www.w3.org/TR/websub/)）。强化学习或学习式抓取调度：这类方法是为 Bing 那种 1,800 万 URL 规模下的带宽分配设计的（[Microsoft Optimal Freshness Crawl](https://microsoft.github.io/Optimal-Freshness-Crawl-Scheduling/)）。在升级 SQLite 之前上 Litestream：它会用长读事务接管 checkpoint，而且官方声明 Windows 不是受支持平台（[Litestream releases](https://github.com/benbjohnson/litestream/releases)）。LiteFS：Fly 称无法提供支持（[Fly 社区](https://community.fly.io/t/what-is-the-status-of-litefs/23883)）。另外还有完整的 Merkle 透明日志、代理轮换、huey 队列、纯 LLM 聚类、对 4,000 条做全量 pairwise 排序，以及任何非商用许可的资产进入可分发产物。

已经做对、不必重做的部分也值得点明。失败后的指数退避封顶 6 小时（`app/crawler/runner.py`），与 CommaFeed、NewsBlur 同类。#179 的静默源判定按每个源自身历史间隔的 1.5 倍判断，比 Huginn 固定的 `expected_update_period_in_days` 更自适应（[Huginn working_helpers.rb](https://github.com/huginn/huginn/blob/master/app/concerns/working_helpers.rb)）。分析结果发布时校验 `lease_token`（`app/analysis_results.py`），正是 Kleppmann 说的 fencing token（[Kleppmann 2016](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)）。

## 抓取层缺的是条件请求和按主机限流，不是新爬虫

infohub 抓取层的问题集中在 HTTP 礼貌层。`app/crawler/http.py` 对所有请求都伪装成 Chrome UA；遇到 429 固定睡 30 秒、只重试一次，不读 `Retry-After`，也不通知同主机的其他源；RSS 请求从不带条件头。2026-10-07 对真实信源的探测显示，条件请求能救下大约一半的 RSS，但救不了流量的大头。**TechCrunch、量子位、DeepMind 博客、美联储货币政策 feed 对条件请求都返回 304**（[TechCrunch](https://techcrunch.com/feed/)、[量子位](https://www.qbitai.com/feed)、[DeepMind](https://deepmind.google/blog/rss.xml)、[Fed](https://www.federalreserve.gov/feeds/press_monetary.xml)）。IT之家（[ithome.com/rss](https://www.ithome.com/rss/)）和 Google News RSS 则根本不发校验头，Google News 还带着 `no-store`（[news.google.com](https://news.google.com/rss/search?q=NVIDIA+when:2d&hl=en-US&gl=US&ceid=US:en)）。而 Google News 正是 23 个公司源、每 20 分钟一次的主力（`app/crawler/sources.py`）。Ars Technica 发了 `Last-Modified`，对条件请求却仍回 200（[Ars feed](https://feeds.arstechnica.com/arstechnica/index)）。所以应当照搬 **Miniflux 的双重判断**：304 视为未变；收到 200 时，再拿返回的 ETag/Last-Modified 和库里存的值比一次（[Miniflux response_handler.go](https://github.com/miniflux/v2/blob/main/internal/reader/fetcher/response_handler.go)）。对不发校验头的源可以退一步：对响应体或排好序的条目 ID 列表取哈希，没变就跳过解析和写库。这是研究中的推断，两个参考项目都没有完全这样做。feedparser 的 `parse(url, etag=..., modified=...)` 已经原生支持 304（[feedparser 文档](https://github.com/kurtmckee/feedparser/blob/develop/docs/http-etag.rst)）。

**按主机共享 `Retry-After` 是对 Google News 最有用的一条**。FreshRSS 1.27.0 开始遵守 429/503 的 `Retry-After`，1.28.0 起把它扩到整个域名（主机 + 端口），代理单独处理，本地网络排除在外（[FreshRSS CHANGELOG](https://github.com/FreshRSS/FreshRSS/blob/edge/CHANGELOG.md)）。Miniflux 的 `ParseRetryDelay()` 同时接受秒数和 HTTP 日期两种写法（[Miniflux handler.go](https://github.com/miniflux/v2/blob/main/internal/reader/handler/handler.go)）。CommaFeed 取 `max(Retry-After, 错误退避)`（[FeedRefreshIntervalCalculator.java](https://github.com/Athou/commafeed/blob/master/commafeed-server/src/main/java/com/commafeed/backend/feed/FeedRefreshIntervalCalculator.java)）。23 个 Google News 源共用一个主机，一次 429 就应该让它们一起暂停，而不是各自再撞一次。reader（Python，BSD-3）给调度间隔加随机抖动，让各源的更新不在同一时刻发生；它还提醒，不持久化 feed 状态会反复下载没变的内容，"发布方可能封禁你"（[reader 指南](https://reader.readthedocs.io/en/latest/guide.html)）。这些头的语义见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) 和 [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111)。FreshRSS 是 AGPL-3.0，只读它的变更日志，不抄代码。

**按出新频率自适应的间隔**是第二个杠杆。Miniflux 的 `entry_frequency` 调度器用"7 天 ÷（每周条目数 × 系数）"计算间隔，夹在 5 分钟到 1,440 分钟之间（[Miniflux 配置文档](https://miniflux.app/docs/configuration.html)）。CommaFeed 的"经验间隔"按最近一次发布距今多久分档拉长间隔（[CommaFeed](https://github.com/Athou/commafeed/blob/master/commafeed-server/src/main/java/com/commafeed/backend/feed/FeedRefreshIntervalCalculator.java)）。Media Cloud 发现新文章后 5 分钟内再抓，没有新文章就 10、20 分钟逐步退避，最长到每周一次，一有新文章就重置（[Media Cloud, arXiv 2104.03702](https://arxiv.org/abs/2104.03702)）。对 infohub 来说，冷门公司的 Google News 源可以放宽到 1–2 小时，热门公司保持 20 分钟，这样能直接降低触发 Yahoo 式 429 的请求量。限制条件是：间隔必须小于"feed 窗口条数 ÷ 峰值出新速度"，否则条目会滑出窗口。快讯源的这个问题已由 #175 的回补解决。论文里的变化率估计也给了一条提醒：朴素的"检测到的变化次数 ÷ 时间"估计量是有偏且不一致的（[Avrachenkov et al., arXiv 2009.08142](https://arxiv.org/abs/2009.08142)）。不过 RSS 能直接数每次新增的条目，所以用带上下限的滑动均值就够了。

**监控要看输出，不只看 HTTP 成功**。Zyte 的 Spidermon（BSD-3）内置了几类监控：条目数、字段覆盖率（`FieldCoverageMonitor`）、jsonschema 校验、不该出现的 HTTP 状态码，以及与历史运行对比条目数（[Spidermon monitors.py](https://github.com/scrapinghub/spidermon/blob/master/spidermon/contrib/scrapy/monitors/monitors.py)）。照这个思路，infohub 每次抓取可以检查四件事：条目数是否为 0；标题、URL、发布时间、摘要的覆盖率；财联社、华尔街见闻、新浪这几个逆向 API 的响应 schema（字段改名是这类接口最常见的坏法）；以及"HTTP 200 但返回的是 HTML 验证页"的情况，Miniflux 把它单独报成 `feed_format_not_detected`（[Miniflux handler.go](https://github.com/miniflux/v2/blob/main/internal/reader/handler/handler.go)）。#179 能发现单个源沉默，但发现不了整台机器停摆。infohub 自己的审计显示，采集器在 356 小时里有约 40 小时因为 Mac 睡眠而空转。这类问题要靠**机器外的 dead-man switch**：每轮调度成功后 ping 一次 Healthchecks（BSD-3，10,386 stars，v4.4），超时没收到就告警（[Healthchecks](https://github.com/healthchecks/healthchecks)）。Healthchecks 应该用托管版或另一台机器，和 infohub 放在同一台主机上就失去了意义。RSSHub 维持上千个连接器靠的是每周一次、外加每个 PR 都跑的线上路由测试；它的贡献者守则明确说不要写路由单元测试，因为那只编码了作者对目标站的假设（[test-full-routes.yml](https://github.com/DIYgod/RSSHub/blob/master/.github/workflows/test-full-routes.yml)、[AGENTS.md](https://github.com/DIYgod/RSSHub/blob/master/AGENTS.md)）。infohub 可以照做一个每周的连接器自检，断言输出形状和非零条目数，同时关注 newsnow 和 RSSHub 中财联社、华尔街见闻目录的提交。上游一修，往往就说明接口变了。

**许可证要清理一处**。`app/crawler/fastnews.py` 的文件头注明财联社签名"抄自 RSSHub"（`lib/routes/cls/utils.ts`），而 RSSHub 是 AGPL-3.0（[RSSHub cls 路由](https://github.com/DIYgod/RSSHub/tree/master/lib/routes/cls)）。newsnow（MIT，现已迁到 newsnext 组织）实现了同样的 `md5(sha1(querystring))` 签名，参数为 `appName: "CailianpressWeb"`，并使用 `get_roll_list` 端点（[newsnow cls/utils.ts](https://github.com/newsnext/newsnow/blob/main/server/sources/cls/utils.ts)）。以它为参照重写并附上 MIT 声明，就能消除 AGPL 衍生的疑问。这是工程判断，不是法律意见。UA 也值得重新考虑：RSSHub 默认用随机的 Chrome UA（[RSSHub 配置](https://docs.rsshub.app/deploy/config)），infohub 目前的做法与之相同。对西方 RSS 发布方，一个固定且带联系方式的 UA 更礼貌，SEC 也本来就要求这样做，`sec_source.py` 已经照办。浏览器式请求头只留给确实需要它的中文 API。被封的源应该降频，而不是加代理：NewsBlur 对被封的 feed 把最短间隔拉到 3–24 小时（[NewsBlur models.py](https://github.com/samuelclay/NewsBlur/blob/master/apps/rss_feeds/models.py)）。

正文抽取排在后面，因为 infohub 主要靠标题加摘要做判断。真要抽正文时，英文用 trafilatura（Apache-2.0，维护者自测 F1 0.926，[trafilatura 评测](https://trafilatura.readthedocs.io/en/latest/evaluation.html)）。中文不能只靠它：SIGIR 2025 的多语评测中，trafilatura 在中文上的 F1 只有 **0.555**，Readability 是 0.672；**67% 的中文页面**至少有一个抽取器得分 ≤0.1，英文页面只有 8%（[SIGIR 2025 论文](https://maurelf.users.greyc.fr/docs/conferences/SIGIR_2025_paper_1968.pdf)）。中文重点站点适合按站点写 CSS 选择器（FreshRSS 的 `cssFullContent` 思路，[FreshRSS OPML 文档](https://github.com/FreshRSS/FreshRSS/blob/edge/docs/en/developers/OPML.md)），通用兜底用 readability-lxml（Apache-2.0）。GNE 是 GPL-3.0，它"接近 100% 准确"是自称（[GNE](https://github.com/kingname/GeneralNewsExtractor)），只能按它所依据的论文自己实现。URL 规范化可以直接用 courlan（Apache-2.0，[courlan](https://github.com/adbar/courlan)）。

## 去重与聚类：给 titles-v3 加时间核、学习式判定和定时合并

titles-v3 用"字符三元组 + 时间窗 + 实体提示"作主干，这个方向被证据支持；它缺的是三样东西：时间特征、学出来的"是否新建 story"判定，以及事后合并。**Miranda 2018**（EMNLP，Priberam）是多语流式新闻聚类的事实标准。它的做法是：每种语言内部在线聚类，文档用词、词元、命名实体三组 TF-IDF 表示，再加上与簇内最新、平均、最旧时间之差的三个高斯时间特征（σ 调到 72 小时）；特征权重用 SVM-rank 学；"是否新建簇"由单独的 SVM 决定。结果是英文 F1 **94.1**。改用网格搜索阈值来决定是否新建，F1 只有 **82.8**；把跨语言 embedding 直接用于单语聚类，只有 74.8（[Miranda et al. 2018](https://homepages.inf.ed.ac.uk/scohen/emnlp18cluster.pdf)）。Saravanakumar 2021 的消融结果更直白：只用 TF-IDF 是 86.36，加上时间特征到 91.72；只用稠密向量是 68.98，加上时间也只有 82.73。作者的解释是，稠密表示会把"同主题、不同事件"的文章并到一起，例如两场不同的足球赛（[arXiv 2101.11059](https://arxiv.org/abs/2101.11059)）。Miranda 的代码是 BSD-3，但只有 40 stars、2022 年后不再维护（[Priberam/news-clustering](https://github.com/Priberam/news-clustering)），所以读论文就够了。

反方证据来自 **Škvorc 2025**（媒体监测公司 Kliping）。在离线 k-means、斯洛文尼亚语的设定下，BGE-M3 的 AMI 为 0.838，TF-IDF 只有 0.603；但在线算法全面崩溃，DBSTREAM 只有 0.162。作者的补救办法是"聚类后优化"：反复把中心距离小于阈值的簇合并。另一个发现是，先用 LLM 写摘要再做 embedding 反而更差（AMI 0.780），而且更慢（[arXiv 2508.08272](https://arxiv.org/abs/2508.08272)）。两组研究的设定不同，并不矛盾，合起来的结论是：**embedding 适合当附加特征和跨语言桥梁；"大幅改写的稿件没合并"最直接的解法是定时合并**。Event Registry 还有三个细节可以直接搬（[Leban et al., WWW 2014](https://archives.iw3c2.org/www2014/proceedings/companion/p107.pdf)）：聚类时实体权重远高于普通词；超过 k 天的簇退出聚类器，但不从事件库删除；事件标题取最接近簇中心的那篇文章（medoid），事件日期取文中最常提到的日期，否则取平均日期，刻意不用最早日期，以免被误并入的旧文把时间线拉早。最后这一点对 infohub 的持久时间线尤其重要。

**三家中文快讯同发**适合在 titles-v3 前面加一层便宜的过滤。先规范化：去掉"财联社X月X日电"、【】、来源前缀，统一全角/半角，然后做精确哈希。再在同语种、24–72 小时窗口内，同时计算字符 2–3 元组的 Jaccard 和包含度（交集 ÷ 较短者），后者专门处理"短快讯对稍长改写"的情况。text-dedup（Apache-2.0）默认的 5-gram、阈值 0.7 是为长文档设定的（[text-dedup](https://github.com/ChenghaoMou/text-dedup)）。中文从业者经验认为，SimHash 的"汉明距离 ≤3"在短文本上召回差（[知乎](https://zhuanlan.zhihu.com/p/51464268)，属博客级证据）。NEWS-COPY 基准给了基调：MinHash 的 ARI 为 0.737–0.783，不微调的 mE5-base 为 0.742，两者打平；真正拉开差距的是对比学习微调的 bi-encoder（0.915）加 cross-encoder 重排（0.937）（[Silcock et al., arXiv 2210.04261](https://arxiv.org/abs/2210.04261)、[RETSim, arXiv 2311.17264](https://arxiv.org/html/2311.17264)）。专门处理"只有标题加短摘要"新闻的 **NDD-MAC**（NAACL 2025 Industry）建议，在真实新闻流上把阈值设在 0.85–0.9，并按 3–4 天的滑动窗口处理，效果更好、计算更省（[NDD-MAC](https://aclanthology.org/2025.naacl-industry.73.pdf)）。72 小时窗口大约 1.2 万条，精确计算即可，datasketch（MIT）只是一个方便的选项，不是性能上的必需。

改造后的流水线如下。先做 blocking：按语言和时间窗，用字符 shingle 倒排、实体 ID 倒排，再加上 embedding top-k 补召回。然后对每个"条目 → story"对计算特征：三元组 Jaccard 和包含度、实体重合、与 story 中心向量的余弦、高斯时间核、是否同一发布方，用逻辑回归打分。决策分三带：高分直接并入，低分新建，中间灰区让 GLM 回答 yes/no，结果按条目对的哈希缓存，并设每日上限。最后每小时对近 72 小时的 story 跑一次合并。Priberam 让新文档只和簇中心比，不和簇里的每一篇比，这是控制成本的关键（[Miranda 2018](https://homepages.inf.ed.ac.uk/scohen/emnlp18cluster.pdf)）。LLM 只当"有噪声的标注者"，用来生成成对约束或复核灰区（[Viswanathan et al., TACL 2024](https://aclanthology.org/2024.tacl-1.18/)、[Cequel, arXiv 2504.15640](https://arxiv.org/abs/2504.15640)），不让它对每条直接聚类。按灰区占 5% 推算，每天约 200 次短调用。

**中英同一事件**在 story 层面链接，不在条目层面。SemEval-2022 Task 8 的评测集里有中文 769 对、中英 213 对，都只出现在评测阶段。最好成绩 Pearson 0.818；不微调、直接用预训练 embedding 可以到 0.759；只用"共享实体 + 文章余弦"两个特征的回归也有 0.677（[SemEval-2022 Task 8 综述](https://aclanthology.org/2022.semeval-1.155.pdf)）。Miranda 的经验是，不同语言对要用不同阈值：以英文为枢轴时跨语言 F1 为 84.0，用全局阈值只有 72.7。推荐的判据是：至少共享一个规范化实体（ticker 或公司 ID）、代表标题的余弦超过单独设定的跨语言阈值、最早时间相差 24–48 小时以内，灰区交给 GLM。SemEval 上最好的系统都结合了机器翻译，infohub 只需翻译每个 story 的代表标题，每天几百次。模型选择如下（许可证来自 Hugging Face）：

| 模型 | 许可证 | 参数量 | 定位 |
|---|---|---|---|
| [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small) | MIT | 118M | 默认；输入要加 `query:`/`passage:` 前缀 |
| [BAAI/bge-m3](https://huggingface.co/BAAI/bge-m3) | MIT | XLM-R large 级 | 召回不够时升级；Škvorc 实验中最好 |
| [Qwen/Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B) | Apache-2.0 | 596M | 备选 |
| [sentence-transformers/LaBSE](https://huggingface.co/sentence-transformers/LaBSE) | Apache-2.0 | 471M | 双语句对；GateNLP 用它在 SemEval 得 0.801 |
| [jinaai/jina-embeddings-v3](https://huggingface.co/jinaai/jina-embeddings-v3) | CC BY-NC 4.0 | 572M | 不用（非商用） |

每天约 4,000 条短标题，在 CPU 上推理也只需几分钟，72 小时窗口内用 numpy 暴力算余弦即可，不需要 ANN 索引。这是推算，需要在主机上实测。

**评测和 ID 稳定性**有现成规范可循。Amigó 等证明，B-cubed 是唯一满足四条形式约束的外部聚类指标（[Information Retrieval 2009](https://link.springer.com/article/10.1007/s10791-008-9066-8)），python-bcubed（Apache-2.0）可直接使用（[python-bcubed](https://github.com/hhromic/python-bcubed)）。但 B-cubed 对碎片化不敏感：一个模型产生 276 个簇、另一个产生 484 个（真实为 222），B-cubed 只差 0.35（[arXiv 2101.11059](https://arxiv.org/abs/2101.11059)）。所以要同时报告成对 P/R 和"预测簇数 ÷ 真实簇数"，后者正好监控"改写稿没合并"的问题。标注量建议如下：按当前打分分层抽 300–500 对，另留 100–200 对跨语言样本，再完整标注 10–20 个 story；每次改动匹配器，都在这份冻结的标注集上回放比较。story_id 创建后不再改变；合并时让较早的 story 作为 canonical，另一个记 `merged_into`，查询时用并查集解析；如果换模型需要批量重聚类，就用最大重叠（Hungarian 匹配）把新簇映射回旧 ID（[R-bloggers](https://www.r-bloggers.com/2012/11/matching-clustering-solutions-using-the-hungarian-method/)）。Kliping 原来在每次查询的结果集上临时聚类，story 随时间漂移，改成全库增量聚类后才稳定下来（[arXiv 2508.08272](https://arxiv.org/abs/2508.08272)）。

## 相关性与重要性：先盯误报，120 条测试集只能抓大错

关于 LLM 做标注者，结论是"能用，但必须逐任务验证"。乐观的一面：零样本 ChatGPT 在包括相关性在内的 5 个任务中有 4 个胜过众包标注（[Gilardi et al., arXiv 2303.15056](https://arxiv.org/abs/2303.15056)）；Bing 用真实搜索者的标注调过 prompt 后，LLM 标签"与人工标注者一样好"，但**仅仅换一种说法改写 prompt 就会改变准确率**（[Thomas et al., arXiv 2309.10621](https://arxiv.org/abs/2309.10621)）。另一面：在固定任务上，微调的小模型普遍胜过零样本 LLM（[Bucher & Martini, arXiv 2406.08660](https://arxiv.org/abs/2406.08660)、[Edwards & Camacho-Collados, arXiv 2403.17661](https://arxiv.org/abs/2403.17661)）；"LLM hacking"研究复现了 37 个标注任务，用最先进的 LLM 时约 **31%** 的假设得出了错误结论（[Baumann et al., arXiv 2509.08825](https://arxiv.org/abs/2509.08825)）。对 infohub 最直接的一条来自 TREC 2024 RAG：**人类评估者比 LLM 评估器更严格**（[arXiv 2411.08275](https://arxiv.org/abs/2411.08275)）。由此推断，GLM 会把更多条目判成"相关"，所以在站长标注的测试集上，第一个要看的指标是"相关"和"≥70 精选"的精确率。infohub 定下的"silver 标签永不当真值"，与这些研究的共识一致（[Pangakis et al., arXiv 2306.00176](https://arxiv.org/abs/2306.00176)）。

**把标注器当成带版本的产物来管**。同一个"GPT-4"服务在 2023 年 3 月到 6 月之间，质数判断准确率从 84% 掉到 51%（[Chen et al., arXiv 2307.09009](https://arxiv.org/abs/2307.09009)）。2026 年 10 月的一项研究发现，**只换评分量表就能让测得的偏差移动最多 0.93 分，而模型身份是方差的最大来源**（[Vaugrante & Hagendorff, arXiv 2610.05094](https://arxiv.org/abs/2610.05094)）。所以要钉死模型 ID、prompt 哈希、温度和量表，任何一项变更都要在固定的 canary 集（例如 120 条 dev）上重跑并比较标签分布；在 dev 上跑 2–3 次测自一致性（[Reiss, arXiv 2304.11085](https://arxiv.org/abs/2304.11085)）。报告时用 κ 加各类别的 P/R，不要只报原始一致率，因为高一致率可能掩盖很不同的打分（[Thakur et al., arXiv 2406.12624](https://arxiv.org/abs/2406.12624)）。

**0–100 的重要性分默认是没有校准的**。Li 等在 6 个基准上比较了 0–5、0–10、0–100 三种量表，**0–5 与人类的一致性最好**（[arXiv 2601.03444](https://arxiv.org/abs/2601.03444)）。LLM 评分的分布本身就偏斜，而且在多属性判断之间会相互锚定（[Stureborg et al., arXiv 2405.01724](https://arxiv.org/abs/2405.01724)），而 infohub 正是在一个 prompt 里同时要相关性、类别和重要性。建议改成带锚点的 0–5 级，例如 5 = 对关注股票有市场影响的消息或重大 AI 发布，0 = 无影响。如果接口提供 logprobs，就按 G-Eval 的做法用 token 概率求期望分（[G-Eval, arXiv 2303.16634](https://arxiv.org/abs/2303.16634)）；否则采样 2–3 次取平均，展示时再映射回 0–100。阈值用站长标签做单参数逻辑回归（Platt）校准，按目标精确率定切点；保序回归需要更多数据，现阶段不合适。排序方法上，pairwise 比 pointwise 准，在 BEIR 上 NDCG@10 高出 10% 以上（[PRP, arXiv 2306.17563](https://arxiv.org/abs/2306.17563)），但更贵，而且在干扰特征下 **pairwise 的偏好有 35% 会翻转，绝对打分只有 9%**（[Tripathi et al., arXiv 2504.14716](https://arxiv.org/abs/2504.14716)）。所以全量仍用 pointwise，只在 55–85 分的边界带内做 pairwise，并且两种顺序都问一遍（[Wang et al., arXiv 2305.17926](https://arxiv.org/abs/2305.17926)）。"重要新闻"数据集普遍报告标注者分歧很大（[KhabarChin, arXiv 2312.03361](https://arxiv.org/abs/2312.03361)），说明重要性本身是主观的，infohub 唯一有效的真值就是站长自己的判断。

**样本量决定能看出多大的差别**。小样本下应该用 Wilson 区间，不用 Wald 区间（[Brown, Cai & DasGupta 2001](https://projecteuclid.org/journals/statistical-science/volume-16/issue-2/Interval-Estimation-for-a-Binomial-Proportion/10.1214/ss/1009213286.full)）。按 Wilson 公式计算：

| 样本 | 观测值 | 95% Wilson 区间 | 半宽 |
|---|---|---|---|
| 120 条测试集 | 准确率 0.85 | 0.775–0.903 | ±6.4 个百分点 |
| 30 条预测为正 | 精确率 0.80 | 0.627–0.905 | ±13.9 个百分点 |
| 60 条预测为正 | 精确率 0.80 | 0.682–0.882 | ±10.0 个百分点 |
| 360 条 | 0.85 | 0.809–0.883 | ±3.7 个百分点 |

也就是说，120 条测试集足以发现严重失效，但分辨不出两个只差几个点的标注器版本。自复核的 κ 也有同样的问题：κ 受类别比例影响，"相关"越稀少，要的样本越多（[Sim & Wright 2005](https://research.birmingham.ac.uk/en/publications/the-kappa-statistic-in-reliability-studies-use-interpretation-and/)）；类别偏斜时，还会出现一致率很高而 κ 很低的悖论，解决办法是同时报告正一致率和负一致率（[Cicchetti & Feinstein 1990](https://www.jclinepi.com/article/0895-4356(90)90159-M/abstract)）。所以和 0.70 门槛比较的应该是 κ 的置信区间，而不只是点估计。

**统计方法能让站长的每条标签多发挥作用，但收益有上限**。prediction-powered inference（PPI）把少量真值标签和大量模型预测结合起来，给出可证明有效的置信区间（[Angelopoulos et al., arXiv 2301.09633](https://arxiv.org/abs/2301.09633)）。分层 PPI 在标注器质量随分层变化时，区间明显更窄（[arXiv 2406.04291](https://arxiv.org/abs/2406.04291)）。AutoEval 把有效人工样本量最多提高 50%（[arXiv 2403.07008](https://arxiv.org/abs/2403.07008)）；confidence-driven inference 能省下 25% 以上的人工标注（[arXiv 2408.15204](https://arxiv.org/abs/2408.15204)）。但有两条警告。第一，**当评判者不比被评系统更准时，任何去偏方法最多只能把所需真值标签减半**（[Dorner, Nastl & Hardt, arXiv 2410.13341](https://arxiv.org/abs/2410.13341)）。第二，标签稀少时，PPI++ 甚至可能比经典方法更差（[Eyre & Madras, arXiv 2411.12665](https://arxiv.org/abs/2411.12665)）。所以应该同时报告 PPI 区间和 Wilson 区间，并事先定好选用规则。design-based 校正要求每条样本被抽中的概率已知（[DSL, arXiv 2306.04746](https://arxiv.org/abs/2306.04746)），因此 600 条样本的分层入样概率现在就要记录下来。测试集保持固定、不变；主动挑样（[active testing, arXiv 2103.05331](https://arxiv.org/abs/2103.05331)）只用于额外的 train/dev 或单独的审计集。在策划过的测试集里，标签错误平均也至少有 3.3%，confident learning 标出的候选中 51% 确认是错误（[Northcutt et al., arXiv 2103.14749](https://arxiv.org/abs/2103.14749)），所以对 360 条 silver 训练标签跑一次 cleanlab 很划算。标注标准会在打分过程中漂移（[EvalGen, arXiv 2404.12272](https://arxiv.org/abs/2404.12272)），所以标测试集前要先冻结一份书面细则，并用 train/dev 先做一批热身。

工具层面，ppi_py（MIT，约 300 stars）提供 `ppi_mean_ci`、Cross-PPI 和功效分析 notebook（[ppi_py](https://github.com/aangelopoulos/ppi_py)）。cleanlab 在 **2025-12-16 从 AGPL-3.0 改为 Apache-2.0**，要钉在改许可之后的版本（[LICENSE 历史](https://github.com/cleanlab/cleanlab/commits/master/LICENSE)）。SetFit（Apache-2.0）可作为学生模型（[SetFit](https://github.com/huggingface/setfit)）。Argilla 和 Label Studio 都是 Apache-2.0，但要多维护一个服务，现有的 `label.sh` 已经够用；如果以后要换，测试集绝不能显示 silver 建议，否则就不再是盲标。

成本是最后一层。学习式级联能在准确率持平的情况下大幅降本：FrugalGPT 最多省 98%（[arXiv 2305.05176](https://arxiv.org/abs/2305.05176)），online cascade learning 最多省 90%，而且对分布漂移稳健（[arXiv 2402.04513](https://arxiv.org/abs/2402.04513)）。GLM-4.6 在 Z.ai 的价格是每百万 token 输入 0.6 美元、缓存输入 0.11 美元、输出 2.2 美元（[Z.ai 定价](https://docs.z.ai/guides/overview/pricing)）。智谱 Batch API 半价，但文档没有列出 GLM-4.6（[BigModel Batch](https://docs.bigmodel.cn/cn/guide/tools/batch)）。按每条 800 个输入 token、300 个输出 token 粗算，每天约 4.6 美元，大头在输出，所以"只给通过相关性的条目写摘要"是最省事的一刀。这里的判断是：在这个规模下，学生模型的主要价值不是省钱，而是充当第二意见和漂移探测器。它和 GLM 的分歧率突然升高，就是 prompt、模型或新闻分布变了的信号。

## 金融新闻：监管方已经免费给出了事件标签

**SEC 这条线已经合规，还能加两层**。官方规则只有两条硬性要求：不超过 10 次/秒，以及 User-Agent 里声明联系邮箱；submissions API 的更新延迟不到一秒，不需要 API key（[SEC EDGAR APIs](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)、[Accessing EDGAR Data](https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data)）。infohub 每 10 分钟拉一次 submissions JSON，并带上配置好的 `SEC_USER_AGENT`（`app/crawler/sec_source.py`），符合规则。可以加的两层是：用 `daily-index` 每日对账补漏；用 getcurrent Atom 做低延迟触发（这一点目前只有第三方页面描述，[Apify](https://apify.com/darthdimus/sec-edgar-current-filings)，需要实测）。更有价值的是，**8-K 的 item 编号本身就是监管方给的事件类型标签**（财报、并购、高管变动等），可以作为 LLM 事件分类的弱监督和校验。edgartools（MIT，约 2.8k stars）能解析 8-K items、Form 4 和 13F，并用 `set_identity()` 集中配置 UA（[edgartools](https://github.com/dgunning/edgartools)）。submissions JSON 里是否带 items 字段，还没有核实。

**港交所和巨潮都没有找到官方 API**。港交所披露易的 Title Search 用三级 Headline Category 分类（2007-06-25 之后第一级有 16 类，例如"须予公布的交易 → 非常重大的收购"）。不指定股票代码时，检索期不能超过 1 个月；指定股票代码时可以回溯到 1999-04-01（[HKEXnews Title Search Guide](https://www2.hkexnews.hk/-/media/HKEXnews/Homepage/Listed-Company-Publications/Search-Guide/TitleSearchGuide_e.pdf)）。因此应按股票代码轮询，并把 Headline Category 原样入库，作为第二个官方事件标签来源。巨潮常用的 `hisAnnouncement/query` 是社区逆向出来的接口（[CSDN 教程](https://blog.csdn.net/weixin_44566452/article/details/121039032)），在观察名单里主要只和中芯国际的 A 股有关，应该低频按代码查询，并保存原始响应。OpenBB 是一个反面教训：v5.0.0 删除了 benzinga、fmp、intrinio、tiingo 等新闻扩展，`obb.news.world` 直接不可用（[OpenBB v5.0.0](https://github.com/OpenBB-finance/OpenBB/releases/tag/openbb-v5.0.0)）。新闻链路应该尽量直连一手来源，不要押在某个数据商的 SDK 上。

**公司识别没有现成的中英文"新闻 → ticker"链接器可用**，成熟做法是"小型人工身份表 + 过滤词 + 少量 LLM 复核"。RepLab 2013 的实体过滤任务就是判断一条文本是否真的指向某家公司（[RepLab 2013](http://nlp.uned.es/replab2013/)）。UNED 团队发现，"正/负过滤词"（出现即高概率相关或无关的表达）是很有竞争力的方法（[UNED at RepLab 2013](https://ceur-ws.org/Vol-1179/CLEF2013wn-RepLab-SpinaEt2013.pdf)）。SEntFiN 附带一个"1,000+ 实体、5,000+ 种表述"的别名库（[arXiv 2305.12257](https://arxiv.org/abs/2305.12257)）。对 infohub 来说，可以给每家公司补上 `positive_context`（例如"理想汽车 / Li Auto / 李想 / MEGA"）和 `negative_context`（例如"理想状态 / 小米粥 / apple pie"），只有苹果、小米、理想、Meta、Arm 这类歧义别名才调用 LLM，并要求 LLM 引用触发判断的原文片段。一项 2024 年的研究用"LLM 抽 ticker + 字符串相似度校验"，在 5,530 篇新闻中有 90% 没有漏掉 ticker，还有 22% 找到了数据商遗漏的 ticker（[arXiv 2407.15788](https://arxiv.org/abs/2407.15788)）。对应到 infohub，规则就是：LLM 给出的公司，必须能在原文中找到别名命中，否则降级为待审。身份层可以用 Wikidata 的 P249/P414/P5531（[Wikidata P249](https://www.wikidata.org/wiki/Property:P249)）和 OpenFIGI 的免费映射（[OpenFIGI API](https://www.openfigi.com/api/documentation)）做一次性离线核对，固化入库后只在 CI 里校验，不在线依赖。

**事件和情感抽取最值得照搬的是 DocFEE 的人机协同流程**。它的步骤是：规则过滤（100% 召回）→ Qwen 预筛 → 多模型生成式标注 + 共识 → 人工迭代修正。标注准确率 84.04%，成本约为纯人工的 0.4%，数据集是 CC BY 4.0（[DocFEE, Scientific Data 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC12065892/)）。这和 infohub"算法大规模出标签、站长是唯一标注者"的分工完全吻合：只把共识不一致或低置信的样本送给站长。证据定位可以借 Google LangExtract（Apache-2.0）的做法，每个抽取结果都映射到原文的精确字符区间（[LangExtract](https://github.com/google/langextract)）；入库时校验 `text[start:end] == quote`，不匹配就拒收。可用的评测集和许可证如下：FinEntity 为 ODC-BY（[FinEntity](https://github.com/yixuantt/FinEntity)）；SEntFiN 的 10,753 条标题中有 2,847 条含多个实体且情感常常冲突，正好对应"英伟达受益、AMD 承压"这类句子（[arXiv 2305.12257](https://arxiv.org/abs/2305.12257)）；Financial PhraseBank 是 **CC BY-NC-SA，只能做内部评测**（[HF](https://huggingface.co/datasets/takala/financial_phrasebank)）；中文的 BDCI 2019 "负面主体判定"格式和 infohub 将来的实体级 tone 几乎一致，但许可证还没核实（[DataFountain](https://www.datafountain.cn/special/BDCI2019/competition)）。模型选择上，FinEntity 发现微调的 BERT-CRF 胜过 ChatGPT-3.5（[arXiv 2310.12406](https://arxiv.org/pdf/2310.12406)），但 2026 年的一项基准称 DeepSeek-R1 和 o1 在实体级金融情感上胜过 transformer 模型（[Springer 2026](https://link.springer.com/article/10.1007/s41060-026-01201-x)，只读到摘要）。所以早期直接用 LLM + 强制引文，积累审核数据后再决定要不要微调小模型。

## 证据与 SQLite：WAL-reset bug 是唯一的紧急项

**这个 bug 的条件和 infohub 完全对得上**。官方原文的意思是：只影响 WAL 模式，且同一个文件上开着两个以上连接（分属不同线程或进程），并且它们在同一瞬间尝试写或 checkpoint。机理是 checkpoint 没有察觉 WAL 已被另一个连接重置，沿用了过期的头信息，导致已提交的页被跳过。修复版本是 3.51.3（2026-03-13），并回移到了 3.44.6 和 3.50.7（[SQLite WAL 文档](https://sqlite.org/wal.html#walresetbug)）。官方说这个时序窗口极窄，但 Tailscale 在六个月里遇到了 **19 次损坏**。他们是靠持续对备份运行 `integrity_check` 才发现的，原因是自己手动做激进的 checkpoint，放大了命中概率；他们的总结是"用非标准方式运行无聊的技术本身就是风险"（[Tailscale 博客](https://tailscale.com/blog/sqlite-wal-reset-bug)）。Debian bookworm 的 libsqlite3 是 3.40.1，trixie 是 3.46.1（[packages.debian.org](https://packages.debian.org/search?keywords=libsqlite3-0&searchon=names&suite=all&section=all)），两者都在受影响区间；第三方汇总称 trixie 没有回移这个修复（[Debian 安全追踪](https://security-tracker.debian.org/tracker/source-package/sqlite3)、[hermes-agent#71851](https://github.com/NousResearch/hermes-agent/issues/71851)）。`Dockerfile` 第一行是 `FROM python:3.12-slim`，所以无论它指向哪个 Debian 版本都受影响。当前在 Mac 上运行的生产解释器链接的是哪个版本还没核实，需要打印出来确认。修复路径按改动量从小到大排：在镜像里编译 ≥3.51.3 的 libsqlite3 并让 `_sqlite3` 链接它；换一个自带新 SQLite 的基础镜像；或者改用静态内置 SQLite 的 APSW（[APSW](https://pypi.org/project/apsw/)），改动最大。同时在启动时断言版本，不满足就拒绝启动。**升级之前，不要新增手动 checkpoint，也不要引入 Litestream**。另外，3.52.0 因为表达式索引问题被撤回，不要用这个版本（[Tailscale 博客](https://tailscale.com/blog/sqlite-wal-reset-bug)）。

**几项 PRAGMA 设置值得调整**。`synchronous=NORMAL` 在 WAL 下不会损坏数据库，但断电或系统崩溃后可能回滚最近几次提交（[PRAGMA synchronous](https://sqlite.org/pragma.html#pragma_synchronous)）。对 infohub 来说，真正的风险在 change_log：如果某个序号在回滚前已经被外部同步方读走，回滚后同一序号可能被新内容复用。除非崩溃恢复后会提升 epoch，否则应保留 FULL。这个取舍此前已经留给站长决定。`journal_size_limit` 默认不限制大小；只要还有读事务开着，checkpoint 就不能重置 WAL（[SQLite WAL](https://sqlite.org/wal.html)），而 6 分钟的备份和 34 秒的校验都会长时间持有读事务。建议设为 64–256 MB。`cache_size` 默认只有约 2 MB，长生命周期的连接可以调到 128–256 MB。长连接在打开时运行 `PRAGMA optimize=0x10002`，之后定期运行 `PRAGMA optimize`（[PRAGMA optimize](https://sqlite.org/pragma.html)）。mmap 不建议开：内存映射文件上的 I/O 错误会直接让进程崩溃（[SQLite mmap](https://sqlite.org/mmap.html)）。追加写入的库几乎没有空闲页，也不需要 VACUUM 或 auto_vacuum。

**迁到 Windows 时，数据库应放在 Docker 命名卷或 WSL 发行版内的路径，不要 bind mount `C:\` 目录**。Docker 官方说明，从 Linux 文件系统挂载的性能"高得多"（[Docker WSL2 最佳实践](https://docs.docker.com/desktop/features/wsl/best-practices/)）。一个个案中，同一条查询在本机是 2.1 ms，走 Windows bind mount 是 196 ms（[GitHub issue #298](https://github.com/mostlypixels/a-vibe-coded-story-organizer/issues/298)）；社区也长期报告 Windows 共享目录上出现 "database is locked"（[docker/for-win#11](https://github.com/docker/for-win/issues/11)）。WAL 本身也不支持网络文件系统。#169 的存储探针已经能回答 U02 这个问题；用命名卷的代价是备份导出流程要重新设计。

**完整性校验与备份**。站长 10 月 5 日决定保留每次启动的完整校验，这里不建议改。要补的是 Tailscale 那一招：每次备份后，在**备份副本**上后台跑完整的 `integrity_check`，并与恢复演练合并，这样不占用主库的读事务。`quick_check` 是 O(N)，`integrity_check` 是 O(N log N)（[PRAGMA integrity_check](https://sqlite.org/pragma.html)）；官方的 cksumvfs 能在读取时发现位翻转（[cksumvfs](https://sqlite.org/cksumvfs.html)），但需要加载扩展并做一次 VACUUM，属于可选项。异地副本推荐 `sqlite3_rsync`：它通过 SSH 只传差异页，内容相近时 500 MB 的库通常只需约 20 KB 流量，3.50.0 起取消了页大小一致等限制（[sqlite3_rsync](https://sqlite.org/rsync.html)），可以经 Tailscale 同步到 NAS。要注意，备份 API 在另一个进程写入时会重启（[Online Backup API](https://sqlite.org/backup.html)），`VACUUM INTO` 是更紧凑的替代（[VACUUM](https://sqlite.org/lang_vacuum.html)）。Litestream v0.5 改用 LTX 文件、支持时间点恢复，但**每个数据库只能有一个副本目标**（[Fly 博客](https://fly.io/blog/litestream-v050-is-here/)）。它用长读事务接管 checkpoint（[Litestream 原理](https://litestream.io/how-it-works/)），只覆盖数据库、不覆盖 CAS 文件，v0.5.17 才移除了 WAL-reset 暴露（[releases](https://github.com/benbjohnson/litestream/releases)），所以只适合在升级之后作为 Linux 侧车容器使用。

**队列和证据格式已经走在正确方向上**。在 WAL 下 IMMEDIATE 与 EXCLUSIVE 等价；读事务升级为写事务时如果遇到写锁，会直接返回 SQLITE_BUSY（[SQLite 事务](https://sqlite.org/lang_transaction.html)）。infohub 已经广泛使用 `BEGIN IMMEDIATE`，并在发布结果时校验 `lease_token`，不需要引入 huey：huey 没有文档化租约重投递语义，它的事务也无法和业务库组合（[huey](https://github.com/coleifer/huey)）。sha256 CAS 与 WARC 的 `WARC-Payload-Digest`（[WARC 1.1](https://iipc.github.io/warc-specifications/specifications/warc-format/warc-1.1/)）以及 Software Heritage 的内在标识（[SWHID](https://docs.softwareheritage.org/devel/swh-model/persistent-identifiers.html)）是同构的。需要互操作时，用 warcio（Apache-2.0）导出 `.warc.gz`，并用 `warcio check` 提供第三方可复核的摘要校验（[warcio](https://github.com/webrecorder/warcio)）；审计接口可以借用 W3C PROV 的 Entity/Activity/Agent 词汇（[PROV](https://www.w3.org/TR/prov-overview/)）。对 change_log，最划算的是一条线性哈希链：每次备份把链头哈希写进清单并同步到异地，epoch 切换时写一条显式的"链重置"记录。tlog-tiles、Tessera 这类 Merkle 透明日志（[C2SP tlog-tiles](https://c2sp.org/tlog-tiles)、[Rekor v2 GA](https://blog.sigstore.dev/rekor-v2-ga/)），只有在需要向第三方出具包含证明时才值得上。

## 同类系统：借产品机制，代码只抄 MIT 和 Apache

开源侧最成熟的是"抓取、转 RSS、热榜聚合"这一层，但这些项目都不做"事件聚类 + 溯源摘要"。做故事级产品的 Kagi、Particle、Ground News、AINews 又只公开产品形态，不公开管线细节。Kagi 的公开仓库和 HN 讨论都没有透露聚类和排序方法（[kite-public](https://github.com/kagisearch/kite-public)、[Hacker News](https://news.ycombinator.com/item?id=45426490)）。所以能借的主要是产品机制。**Kagi News** 每天约 UTC 中午只发一次，理由是给新闻消费一个"自然终点"；先用原文语言生成，再翻译（[Kagi 博客](https://blog.kagi.com/kagi-news)）。它的信源清单是声明式的 `kite_feeds.json`，一个类别至少要有 25 个 feed 才会上线，代码是 MIT，数据是 CC BY-NC 4.0（[kite-public](https://github.com/kagisearch/kite-public)）。对 infohub 的启发是：日报定时发、限定条数；信源注册表做成带版本的声明式文件；每个频道设最低独立信源数作为上线门槛；英文证据先抽 claim，再翻译成中文。**AINews** 同时跑 4 条管线，由编辑挑最好的一份，保留"一层薄的人工策展"（[Heavybit 访谈](https://www.heavybit.com/library/article/ai-hidden-opportunities-for-software-developers-swyx)）；平静的日子直接用 "not much happened today" 作标题（[AINews](https://news.smol.ai/issues/26-01-09-not-much/)）。infohub 可以让日报生成 2–4 个候选，站长挑选的结果写入发布台账，这本身就是偏好标注数据。**Ground News** 为 2,276+ 家媒体手工编码了所有权类型（[Ground News 评级](https://ground.news/rating-system)）。infohub 可以换一个维度做覆盖分布条：中文 vs 英文来源，一手 vs 转载。"英文一手源大量报道、中文源几乎没有"的事件，恰好是中文读者最需要的增量信息。

**热度应以独立信源为主信号**。HN 和 Reddit 的公式都是"互动 × 时间衰减"，Reddit 对票数取对数，所以要多 10 倍的净票才能抵消 12.5 小时的时间差（[Evan Miller](https://www.evanmiller.org/deriving-the-reddit-formula.html)）。Techmeme 由编辑在非独家报道中挑"分析、背景、标题最好"的那篇作主链接（[TechCrunch 2011](https://techcrunch.com/2011/10/31/techmeme-opens-the-kimono-on-how-it-chooses-headlines-and-sources/amp/)）。Google 的 prominence 指"多家信源大量并显著地报道"，而 Full Coverage 页不做个性化（[Google How News Works](https://www.google.com/intl/en_us/search/howsearchworks/how-news-works/)）。infohub 已经按发布方计数（#176 的 PUBLISHERS 注册表），下一步是对数压缩，避免 100 篇转载压倒 3 家独立的一手报道；同时按频道设不同的半衰期（盘中事件几小时，AI 研究 1–2 天）。这是推断，没有现成的同行评审公式可以套用。GDELT 2.0 的 Mentions 表记录了事件被每篇文章提及的时间序列（[GDELT 2.0](https://blog.gdeltproject.org/gdelt-2-0-our-global-world-in-realtime/)），TimelineVol 则报告"匹配数 ÷ 当期全部监测量"（[GDELT DOC 2.0](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/)）。照搬这两点，infohub 可以算出传播速度和首发信源；健康页同时显示原始计数和占总量的比例，就能区分"新闻真的少了"和"我们的采集掉了"。

**LLM 写日报的风险已经被量化**。多文档摘要中，最高可达 **75%** 的内容是幻觉；被要求总结并不存在的话题时，GPT-4o 有 44% 的情况仍然照写；幻觉更多集中在摘要后段（[Belem et al., arXiv 2410.13961](https://arxiv.org/abs/2410.13961)）。EBU 与 BBC 覆盖 18 国的审计发现，**45%** 的 AI 助手新闻回答至少有一个重大问题，来源归因是最大的问题来源（31%）（[EBU 2025](https://www.ebu.ch/news/2025/10/ai-s-systemic-distortion-of-news-is-consistent-across-languages-and-territories-international-study-by-public-service-broadcaste)）。CAMS 的做法是：把来源拆成原子 claim，每个摘要句以能解析回原文片段的 claim ID 结尾，再用独立模型审计引用。多源归因准确率从 38% 提到 64%，人工核验时间降低 3.4 倍；但这是单作者预印本，数字要谨慎看待（[arXiv 2606.23989](https://arxiv.org/abs/2606.23989)）。对 infohub 的落地方式是：在分析版本里加一张 claim 表（claim → 证据版本 → 逐字引文 → 字符区间）；引文必须在全角/半角归一后能字符串匹配到原文，否则该句不得发布；独立信源数不足时输出"信息不足"；对结论句和"影响/展望"类句子加严审核，这类句子在美股频道最容易滑向投资暗示；来源说法冲突时，显式列出分歧。用 LLM 评估日报时，要打乱来源顺序、控制长度，因为 LLM 评判者有位置偏差和冗长偏差（[DiverseSumm, NAACL 2024](https://aclanthology.org/2024.naacl-long.32.pdf)）。

**没有任何同类系统公开漏报率**。Media Cloud 明确承认"分母问题"：不可能知道在线媒体的总体，因此只用相对指标（[arXiv 2104.03702](https://arxiv.org/abs/2104.03702)）。可行的替代是"影子参照集"：每天从维基百科时事门户（WCEP 已把它用作新闻事件参考集，[ACL 2020](https://aclanthology.org/2020.acl-main.120/)）、Techmeme、AIHOT、newsnow 中文热榜、SEC/港交所重大公告里抽样，测 T+2h、T+12h、T+24h 的覆盖率；每条漏报自动归因到三类之一：没采到（信源缺口）、采到但被过滤（阈值问题）、采到但没成事件或排得太低（聚类或排序问题）。这些结果直接进入站长的标注队列。参照集本身有偏，所以只看趋势，不宣称绝对召回率。

## Conclusion

这次调研之后，判断的重心变了。infohub 的核心部分已经达到甚至超过开源同类项目：不可变证据、租约 fencing、版本化标注、按发布方计热度。风险集中在三条边界上：脚下的数据库引擎版本、对信源的 HTTP 礼节、评测之上的统计诚实度。三处都不需要新架构。其中最危险的一处，修复只是换一个 SQLite 版本号。这也说明，下一步该优先排查的是依赖和运行环境，而不是继续给核心加功能。

聚类、相关性、重要性、金融识别这几块反复出现同一个模式：便宜的特征，加一个小的学习式决策，LLM 只处理灰区，人工标签只用在决策会翻转的地方。由此得出的推论是，站长的标注时间是整个系统的瓶颈。它应该通过一条统一的队列流动，按"对决策的影响"排序：阈值附近的相关性样本、灰区的 story 对、跨语言对、影子参照集里的漏报。这样，同一份标注能同时喂给三四个模型和评测，比为每个模块各开一条标注线高效得多。许可证纪律也应该写进架构：AGPL 和 GPL 的工具只能作为独立进程，通过 HTTP 或 RSS 消费其输出，代码永远不进入 infohub 仓库。
